# 🧪 Feature: D365 Export
**Component Scope:** Expense approval flow → Celery task `export_approved_invoice_to_json` → `exports/` directory JSON file → (stubbed real D365 HTTP call)
**Objective:** Verify JSON export generation on approval, file schema correctness, and graceful handling of missing `apps.d365` app.

### 1. Prerequisites & State Setup
- [ ] `D365_MOCK_MODE=true` (essential — real D365 is not configured and `apps.d365` app is missing from the codebase).
- [ ] `exports/` directory exists at project root and is writable.
- [ ] One expense ready to approve (vendor with valid `bc_vendor_no`, OR mock vendor ID).
- [ ] `CELERY_TASK_ALWAYS_EAGER=true` so export task runs inline during test.

### 2. The Happy Path

#### 2.1 Expense approval triggers export
- [ ] As `fin_admin`: approve an expense with `vendor.bc_vendor_no = "BC-123456"`.
- [ ] **Assert Celery task:** `export_approved_invoice_to_json` queued and executed.
- [ ] **Assert file generated:** `exports/<ref_no>.json` exists in project root.

#### 2.2 JSON schema validation
- [ ] Open `exports/<ref_no>.json`; should contain:
  ```json
  {
    "invoiceNo": "BILL-2026-12345",
    "vendorNo": "BC-123456",
    "postingDate": "2026-05-05",
    "description": "…",
    "totalAmount": 100000,
    "lines": [
      {
        "lineNo": 1,
        "amount": 50000,
        "glAccount": "1000",
        "description": "Services"
      },
      ...
    ]
  }
  ```
- [ ] **Assert:** all required fields present; numeric fields are numbers (not strings); dates in YYYY-MM-DD format.

#### 2.3 Mock D365 call (disabled)
- [ ] Approve the expense.
- [ ] **Assert:** JSON file created; no HTTP call to real D365 (because `D365_MOCK_MODE=true`).
- [ ] **Assert logs:** message indicates "D365 MOCK MODE" or similar; no 403/401 from upstream D365.

#### 2.4 Idempotency
- [ ] Approve the same expense twice via API (POST with same body).
- [ ] **Assert:** second approval returns `400` invalid transition OR succeeds but no new JSON file created (record behavior).
- [ ] **Assert:** `exports/<ref_no>.json` has single write timestamp.

### 3. Negative Testing

- [ ] Vendor with `bc_vendor_no=null` → JSON exports with `vendorNo: null` OR error on D365 push (record; should be non-blocking for now).
- [ ] Reject an expense → no export task queued; no file created.
- [ ] Expense with zero total_amount → JSON still generated with `totalAmount: 0`.
- [ ] Expense with `line_items=[]` (empty) → JSON lines array is empty.
- [ ] Invalid line item (missing required fields) → export task handles gracefully (skips or includes partial).

### 4. Edge Cases & Concurrency

- [ ] **File system full:** `exports/` volume has <100 bytes free; export task catches IOError, logs warning, does not crash approval flow.
- [ ] **Concurrent approvals same expense:** impossible by state machine, but if forced (bypass logic), only one export task runs (idempotent).
- [ ] **Unicode vendor names:** vendor name in Chinese; JSON properly encoded as UTF-8 (no mojibake).
- [ ] **Large invoice (1000 line items):** JSON file written successfully; file size <10MB (sanity check).
- [ ] **Special chars in ref_no:** if ref_no contains `..` or `/`, file path is sanitized (no path traversal).
- [ ] **Apps.d365 missing (expected caveat):** if code path tries to import from `apps.d365` without `D365_MOCK_MODE=true`, import fails at startup. **Known issue:** see CLAUDE.md `[VERIFY]` tag.

### 5. Known Issues & Caveats

⚠️ **CRITICAL:** The `apps.d365` application is referenced in `config/settings.py` (INSTALLED_APPS) and `config/urls.py`, but the directory `apps/d365/` does NOT exist. This will cause:
- If `D365_MOCK_MODE=false`, any approval triggers `push_invoice_to_d365` task, which tries to `from apps.d365.tasks import …` → **ImportError at runtime**.
- **Workaround for QA:** Always set `D365_MOCK_MODE=true` to stub the HTTP call.
- **For development:** Either create the missing app or remove the import from `services.py` and mark as TODO.

See CLAUDE.md for full context.
